# BM-001 商机创建与维护

## 1. 目标

维护商机主档、需求、竞争信息、团队、附件及跨系统动作。报价编制和投标执行不在 CRM 内实现，只携带上下文调起报价与投标子系统。

## 2. 业务规则

- 商机号 `SJ + YYYYMMDD + 4 位流水`，服务端生成。
- 必填：名称、客户、类型、来源、预计金额、预计签单日期、负责人、需求摘要。
- 预计金额 `>0`；日期不得早于创建日（历史迁移数据除外）。
- 客户必须有效且在当前数据范围内；负责人和团队成员使用平台 `sub`。
- 一名负责人，可有多名团队成员；变更负责人需原因并通知新旧负责人。
- 保存草稿后即进入 `初步接触/跟进中`；本期不设置商机提交审批。
- 作废与阶段调整一样无需审批，但需权限、原因、依赖校验和审计。
- 最新通过报价与预计金额不一致只提示，不阻断保存或签单。
- 附件只存对象引用，执行病毒扫描、类型和大小限制。
- 创建必须携带 `Idempotency-Key`，并绑定租户、操作人、客户和规范化完整载荷。同键同载荷返回首次创建快照；同键异载荷返回 409，后续主档修改不得改变首次重放响应。

## 3. 数据表

### `crm_opportunities`

`opportunity_no,name,customer_id,type,source,expected_amount,expected_sign_date,requirement_summary,system_count,pain_points,competitor_info,owner_user_id,owner_org_id,current_stage,opp_status,contract_ref,lost_reason,terminal_pending_type,stage_changed_at,end_date`。

枚举：`opp_status=FOLLOWING/CLOSED/VOID`；`terminal_pending_type=NONE/CONTRACT/LOST_REASON`。

子表：

- `crm_opportunity_members(opportunity_id,user_id,role,is_active)`：当前成员投影；
- `crm_opportunity_member_terms(opportunity_id,user_id,role,started_at,snapshot_at,active_at_snapshot,ended_at,started_by,ended_by,source_kind)`：独立任期明细；旧数据的 `LEGACY_SNAPSHOT` 只表达迁移时间与当时活动状态，其加入/移出时间与操作人未知，不伪造连续或重复任期；
- `crm_opportunity_attachments(object_key,file_name,size,mime,scan_status)`；
- `crm_opportunity_change_logs`；
- `crm_opportunity_external_links(type,source_id,status,amount,changed_at,snapshot_json)`。
- `crm_opportunity_create_idempotency(tenant_id,actor_id,idempotency_key,customer_id,opportunity_id,request_hash,response_hash,response_json)`；只保存公共响应快照，不保存认证凭据。

## 4. 后端服务

`OpportunityService`：Create、Update、Void、Restore、ChangeOwner、Add/RemoveMember、CreateExternalLaunchContext、PublishSignedEvent。作废前检查有效售前任务、外部报价/投标和合同关系，并返回可解释阻断项。

转合同不是生成合同草稿：有权用户确认后发布 `OPPORTUNITY_SIGNED` outbox，合同系统按 opportunityId 幂等消费；重复点击返回同一处理结果。

## 6. 前端

页面：商机列表、新建/编辑、详情；详情区包含基本信息、需求、竞争、团队、附件、跟进、阶段、售前任务、外部报价/投标状态。

- “生成报价/发起投标”显示外部系统标识并在新路由打开。
- 金额不一致显示非阻断警告，用户仍可继续。
- 作废弹窗展示依赖检查结果和原因字段。
- 团队编辑使用平台人员选择器，已停用用户只读保留历史。
- 同一规范化创建载荷在当前页面生命周期复用显式幂等键，仅在服务端确认成功后清除；提交期间禁用重复点击，整页重载后的模糊结果先查询服务端状态。

## 7. 验收

- 编号并发唯一；无权访问客户不能创建关联商机。
- 金额不一致只告警不阻断。
- 报价/投标调起携带正确且短效的商机上下文，不泄露内部地址。
- 作废无审批、立即生效，但越权/依赖冲突被后端阻断并全量审计。
- 附件扫描失败不可下载；团队和负责人变更均可追溯。
- 创建响应丢失后同一操作人同键重试不生成第二个编号或商机；同一操作人同键跨客户/异载荷固定冲突。键坐标按操作人隔离，另一操作人可独立使用相同不透明键，但绝不能命中或读取原操作人的响应。

## 8. 当前报价金额提示实现边界（2026-08-02）

- `GET /opportunities/{id}/external-status` 在数据范围校验后，同时返回 `quote_amount_check`；该投影绑定商机当前 `version/expected_amount` 与可信回传的不可变报价快照，不另存可能过期的可写告警状态。
- 仅选择“每张报价单的最新状态仍为 `报价已通过`”的报价，再按 `changed_at,id` 取最新一张；已通过后又失效的报价不会被旧通过记录错误复活。
- 金额按 `DECIMAL(18,2)` 精确比较；不一致返回 `MISMATCH + warning=true`，前端显示黄色提示，但更新主档、进入已签约和转合同的命令链均不读取该标志，因此绝不阻断。
- 已通过报价未携带 `source_amount` 时返回 `APPROVED_QUOTE_AMOUNT_MISSING`，明确为“无法判断”，不猜测金额、不回退到更旧报价。
- 正式报价系统主动查询仍复用现有 `opportunity.status.read` 适配器展示 `latest`；由于正式契约尚未提供“最新已通过报价”的独立权威集合/快照语义，本地金额提示当前以可信 G 回传快照为准，联调时需逐字段确认。

## 9. 当前附件实现边界（2026-08-01）

- `000049` 增加附件对象引用元数据，不在 MySQL 保存二进制；状态为 `PENDING_UPLOAD → FINALIZING → SCANNING → CLEAN/REJECTED/SCAN_FAILED`。
- capability、列表、上传会话、上传完成、受控下载和机器扫描回调均先执行 tenant 与商机数据范围校验；上传、下载、扫描使用独立权限。
- 服务端校验文件名、扩展名、MIME、20 MiB 上限与 SHA-256；只允许 PDF、PNG、JPEG、DOCX、XLSX。对象完成校验必须绑定不可变 object version、大小、MIME 和摘要。
- 扫描器使用附件 public ID 作为稳定幂等坐标；并发完成由持久 `FINALIZING` 抢占，扫描通过前下载固定拒绝。
- 正式对象存储与病毒扫描协议尚未提供。生产 bootstrap 使用明确的 unavailable adapter，创建在任何会话元数据写入前以 503 失败关闭；前端据 capability 禁用上传，绝不伪造可用状态。
