# TS-001 售前技术支持申请创建

## 1. 目标

销售从商机详情或售前列表创建申请，形成“商机—申请—审批—指派—执行—工时”入口。申请只描述资源协调需求，不上传方案、技术标或 POC 文档。

## 2. 字段与校验

| 字段 | 规则 |
| --- | --- |
| request_no | `TS+YYYYMMDD+4位流水`，服务端生成 |
| opportunity_id | 必填；从商机详情进入时预填只读；商机须有效且申请人可访问 |
| applicant_id | 当前登录销售的 OIDC sub，后端取值，不接受前端覆盖 |
| venue | `现场/远程`，必填 |
| service_address | 现场必填，远程可空 |
| contact_name/contact_phone | 必填；电话按当前决议向被指派实施人员明文展示，需隐私审计 |
| description | 必填，去除首尾空白后不得为空；不设置业务字数上限，按接口请求体限制保护；纯文本或安全文本 |
| expected_start/end | 必填，end ≥ start |
| urgency | `普通/紧急` |

申请表不得包含工作内容枚举；工作内容在 TS-005 每笔工时中登记。

## 3. 数据表

`crm_presale_requests`：公共字段外包含 `request_no,opportunity_id,applicant_id,applicant_name_snapshot,venue,service_address,contact_name,contact_phone_cipher,contact_phone_masked,description,expected_start,expected_end,urgency,status,current_approval_node,reject_reason,completed_at,cancelled_at`。

索引：`(tenant_id,request_no)` 唯一；`(tenant_id,opportunity_id)`；`(tenant_id,applicant_id,status,created_at)`。

## 4. 后端与 API

`PresaleRequestService.Create` 校验数据范围，在事务内生成编号、写申请、创建审批实例引用和审计。若通用审批引擎为远程服务，采用 outbox/Saga：本地状态 `APPROVAL_STARTING`，成功后转 `PENDING_APPROVAL`；失败可重试且用户可见，禁止出现无审批实例却显示待审批。

| 方法 | 路径 | 权限 |
| --- | --- | --- |
| POST | `/presale/requests` | presale.create |
| GET | `/presale/requests/{id}` | presale.read + scope |
| GET | `/presale/requests/{id}/contact-phone` | presale.contact_phone.read + 当前/历史真实指派关系，或销售总监/团队负责人/技术负责人 |
| GET | `/opportunities/{id}/presale-create-context` | opportunity.read |

创建接口必须传 Idempotency-Key；相同键重复提交返回同一申请。服务端在查幂等记录前先证明当前账号可见父商机，并把账号、商机和规范化载荷绑定到摘要。前端对同一规范载荷在页面生命周期复用显式键，只在服务端确认成功后清除且提交期间禁止重复点击；整页重载后不得凭空生成键并盲目重发，应先查询申请状态。

联系电话明文只能通过独立按需端点显式查看，普通详情固定返回掩码及服务端计算的 `can_view_contact_phone` 能力位，不得自动解密。明文端点先按 tenant 查询父任务，再同时校验独立 `presale.contact_phone.read` 权限和业务关系：当前、历史执行人均以 PMS 权威 `person_id` 与真实指派记录匹配；明确管理角色为 `sales_director/team_lead/technical_lead`；`auditor` 为显式拒绝，即使叠加其他角色或历史指派也不可查看。申请人关系本身不授予明文权限。

密文通过应用 `SensitiveCodec` 解密并校验掩码绑定；密文损坏、解密器或审计存储不可用统一返回 `CRM_PRESALE_CONTACT_PHONE_UNAVAILABLE`，不得把底层错误或明文写入响应、日志和审计。每次成功查看在返回明文前写 `CONTACT_PHONE_VIEW` 审计，审计仅记录授权关系，不记录电话；审计失败必须关闭返回。所有成功和错误响应均带 `Cache-Control: no-store, private` 与 `Pragma: no-cache`。

## 5. 前端

`PresaleRequestCreate.vue` + `PresaleRequestForm.vue`。从商机详情进入时展示只读商机卡；从列表新建时使用有数据范围过滤的商机选择器。venue 切换动态控制地址必填，提交成功跳任务详情。

任务详情只在 CRM 会话拥有独立权限且服务端能力位为 true 时显示“查看明文”按钮；点击才调用明文端点。明文只保存于当前 Vue 组件内存状态，切换任务或关闭详情立即清除，不写 localStorage、sessionStorage、URL、埋点或调试输出，并允许用户主动隐藏。

## 6. 验收

- 未关联商机、跨范围商机、现场无地址、联系人/电话为空、结束早于开始均被后端阻断。
- request_no 并发唯一；重复提交不生成重复申请。
- 申请人只能由登录身份确定。
- 成功后进入售前两级审批流程；申请表无工作内容和文档上传。
- 联系电话只向有业务关系的执行人/管理者返回明文，所有查看动作审计。
- 跨租户、猜测 ID、非执行人、仅申请人、审计员均无法获得明文；密文损坏或审计失败时无明文响应。
- 普通详情和列表不触发解密；显式查看响应不可缓存，关闭详情后浏览器页面状态不保留明文。
