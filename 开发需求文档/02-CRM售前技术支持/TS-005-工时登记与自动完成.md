# TS-005 工时登记与自动完成

## 1. 最新规则

单人指派时，当前执行人提交首笔有效工时后任务自动完成。多人指派时，所有当前执行人均至少提交一笔有效工时后任务才自动完成。PMS 推送异步执行，推送失败不回滚任务完成，只把对应工时标为待重试。

完成条件定义：

```text
current_assignee_count > 0
AND every current assignee has at least one valid worklog for this task
```

有效工时是已通过业务校验并成功提交本地事务、且未作废的工时；PMS 推送状态不影响其有效性。已结束的历史指派不参与判断。未实际参与的当前执行人必须由团队负责人先移出。

## 2. 输入与换算

| 字段 | 规则 |
| --- | --- |
| person_id | 后端取当前登录人对应 PMS personId，不可前端指定他人 |
| work_start/work_end | 必填，end > start，不允许明显未来时间 |
| raw_unit | `小时/人天` |
| raw_value | `>0`，最多 2 位小数 |
| work_hours | 标准小时；小时原值，人天 × 配置系数，默认 8 |
| work_site_address | 必填；远程可填“远程”或实际地点 |
| work_content | 方案设计/技术交流/POC演示/技术答疑/其他 |
| remark | 可选，最多 1000 字 |

同一人员时间段不得与本任务已有工时重叠；单笔和单日最大值可配置，超限阻断或需特殊权限。

## 3. 数据表

`crm_presale_worklogs`：`worklog_no,request_id,person_id,department_snapshot,person_name_snapshot,work_start,work_end,raw_unit,raw_value,conversion_factor,work_hours,unit='小时',work_site_address,work_content,remark,push_status,push_attempts,idempotency_key,completed_task,created_at`。

不要沿用旧字段名 `raw_hours` 表示人天数；正式模型使用 `raw_value`，对外契约兼容旧名时由 DTO 映射。

## 4. 原子事务顺序

1. 锁定任务并校验 `EXECUTING`、当前执行人和 version。
2. 校验/计算工时，插入 worklog，`push_status=PENDING`。
3. 查询并锁定全部当前指派；插入本笔后判断每名当前执行人是否均存在至少一笔有效工时。
4. 如果条件成立，将任务置 `COMPLETED`、写 completed_at 和状态日志；否则保持 `EXECUTING`。
5. 同事务写 PMS outbox。
6. 提交后由 worker 推送；失败只更新 worklog 推送状态。

重复 Idempotency-Key 返回原 worklog，不重复完成或推送。

## 5. API 与前端

`POST /presale/requests/{id}/worklogs`、`GET /presale/requests/{id}/worklogs`。表单实时展示换算：`1 人天 = 8 小时`（显示当前配置），实施人员只读。提交确认文案按服务端返回的当前指派人数显示：单人任务提示“提交后任务将自动完成”；多人任务提示“所有当前执行人均登记工时后任务自动完成”。

已完成任务仍展示历史工时；当前规则下不再新增后续工时。如业务需要多次累加，必须先变更完成规则，不能绕过状态机。

## 6. 验收

- 1 人天按当前配置准确落为 8 小时，并保留原始单位、数值和换算系数。
- 非当前执行人、非执行中任务、时间重叠、负数/零值均阻断。
- 单人任务首笔有效工时后自动完成。
- 多人任务中，部分执行人登记后仍保持执行中；最后一名未登记的当前执行人提交有效工时后自动完成。
- 工时提交、完成条件判断和任务完成处于同一事务；任一数据库步骤失败全部回滚。
- 移出未参与的当前执行人后如已满足条件，任务在指派变更事务内自动完成。
- PMS 不可用时工时仍成功、任务仍完成，推送状态待重试。
- 幂等重放不生成第二笔工时或第二次完成日志。
