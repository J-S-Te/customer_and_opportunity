# TS-002 售前两级审批

## 1. 规则

本审批只适用于 TS 售前申请，与已取消的商机阶段审批无关。节点固定为：销售总监 → 团队负责人。两节点都通过后状态 `APPROVED_PENDING_ASSIGNMENT`；任一节点驳回后 `REJECTED`，流程终止。

## 2. 状态

```text
PENDING_APPROVAL(node=1)
  ├─ reject → REJECTED
  └─ pass → PENDING_APPROVAL(node=2)
                 ├─ reject → REJECTED
                 └─ pass → APPROVED_PENDING_ASSIGNMENT
```

审批意见通过时可选、驳回时必填。只有当前节点具备对应角色和数据范围的用户可操作；同一节点只能完成一次。

## 3. 数据

- `crm_presale_approval_instances(request_id,engine_instance_id,status,current_node,started_at,finished_at)`。
- `crm_presale_approval_logs(request_id,node,approver_id,approver_name_snapshot,result,comment,approved_at,engine_task_id,request_id_trace)`，唯一 `(tenant_id,engine_task_id)`。

即使复用通用审批引擎，CRM 保存不可变业务投影，详情不依赖审批引擎实时可用。

## 4. 服务与 API

`PresaleApprovalService.HandleCallback` 验证审批引擎机器身份、实例与请求映射、事件序号和幂等键，然后事务更新审批日志与申请状态。人工按钮可调用统一引擎 API，不得直接改 CRM 状态。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/presale/requests/{id}/approval-actions` | 当前节点通过/驳回 |
| GET | `/presale/requests/{id}/approval-history` | 审批时间线 |
| POST | `/internal/approval/callbacks/presale` | 引擎回调 |

action 请求：`action=PASS|REJECT,comment,engine_task_id,version`。

对接前置条件：通用审批引擎必须在启动响应、可信任务分配回调或按 `engine_instance_id + current_node` 查询接口中提供当前节点 `engine_task_id`，并保证调用者只能获得本人可审批任务。CRM 不得要求普通审批人手工抄录内部任务 ID，也不得用实例 ID、售前申请 ID 或上一个节点任务 ID 猜测替代。若引擎只支持按实例+节点执行动作，则双方应先签版新动作契约并由 CRM 服务端解析，浏览器仍不输入内部 ID。缺少该契约时审批按钮必须失败关闭，TS-002 只能算部分实现。

人工审批写入必须携带 `Idempotency-Key`。后端先锁定并校验父任务、当前节点角色与数据范围，再按 `actor + request_id + action + 规范化载荷` 校验重放；相同请求安全返回已入队语义，相同键用于其他执行人、任务、动作或载荷固定返回 409。审批命令 outbox 与不可变幂等协调记录同事务提交，避免重复点击生成多条审批引擎命令。

## 5. 前端

任务详情展示审批时间线、当前节点和意见。只有 `/auth/me` 有权限且后端详情返回 `available_actions` 包含审批动作时显示按钮。前端隐藏按钮不作为安全控制。

## 6. 验收

- 节点顺序不可跳过；实施人员/销售越权审批返回 403。
- 驳回理由必填，驳回后无指派/执行入口。
- 重复回调和重复点击只产生一条日志；乱序回调不改变状态。
- 审批引擎短时不可用时状态可观测并重试，不丢申请。
- TS 审批保留，商机阶段调整界面不得出现本审批能力。
