# TS-003 售前人员指派

## 1. 规则

团队负责人仅对 `APPROVED_PENDING_ASSIGNMENT` 或 `EXECUTING` 任务指派/改派。支持多人，人员来源为基础平台当前有效且已授权给客户与商机应用的用户目录；前端不允许手填 ID，服务端必须再次解析并校验用户。历史指派不删除。

可选角色：技术总监、团队负责人、项目经理、实施工程师。至少一人，重复人员去重。首次指派后任务进入 `EXECUTING`；改派保留完整历史并通知新增/移出人员。

## 2. 多人完成口径

ADR-002 已确认采用“全部当前执行人均登记”规则：

- 单人指派时，该执行人提交首笔有效工时后任务自动完成；
- 多人指派时，只有所有 `is_current=true` 的执行人均至少提交一笔有效工时，任务才自动完成；
- 未实际参与的人员由团队负责人移出当前指派，移出后系统立即按新的当前执行人集合重新判断；
- 已结束的历史指派不参与完成判断；新增当前执行人后必须登记自己的有效工时；
- 完成判断封装在领域服务，策略编码为 `ALL_CURRENT_ASSIGNEES_HAVE_WORKLOG`，禁止散落在 Handler。

## 3. 数据与人员同步

- `crm_presale_engineers(person_id,person_name,department,role,skill_tags_json,contact_cipher,valid_flag,source_updated_at,synced_at)`，唯一 `(tenant_id,person_id)`。
- `crm_presale_assignments(request_id,assignee_id,assignee_name_snapshot,assignee_role,assigned_by,assigned_at,ended_at,is_current,batch_no,change_reason)`。

PMS 同步每 6 小时 + 手动刷新，按 personId upsert。接口失败保留旧缓存并显示数据时间，不清空人员池。

## 4. API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/presale/engineers` | 有效人员池，支持姓名/部门/技能筛选 |
| POST | `/presale/engineers/sync` | 手动刷新，权限 presale.engineer.sync |
| PUT | `/presale/requests/{id}/assignments` | 首次指派或替换当前集合 |
| GET | `/presale/requests/{id}/assignments` | 当前和历史 |

PUT 请求传完整目标人员集合、change_reason、version。Service 锁任务，对比集合：结束移出记录、保留未变记录、新增人员写新记录；不能先全部失效后创建造成瞬时无人。指派集合更新完成后，在同一事务内执行自动完成条件检查；如果剩余所有当前执行人均已有有效工时，则任务立即完成。

每个新增/移出人员须在上述事务内追加不可变指派事件和只含证据 ID 的 outbox。独立 Worker 必须按 tenant 重读任务、指派及证据并校验稳定事件身份，禁止信任 outbox 中的收件人或展示文本；个人通知按基础平台 `person_id` 与 PMS `person_id` 的权威映射投递。缺少 `person_id` 时失败关闭，不得回退到 OIDC `sub/user_id` 猜测同一人员。

新增/移出人员时，同一事务追加 `crm_presale_assignment_events` 不可变事实，并为每名变化人员分别写入 `PRESALE_ASSIGNMENT_SITE_NOTIFICATION` outbox。outbox payload 只含指派事件 ID；专用 Worker 通过该 ID 重新读取 tenant、任务、指派及不可变事实，复核稳定事件身份后投影个人站内通知，禁止信任 payload 中的标题、路径或人员快照。Worker 使用 `FOR UPDATE SKIP LOCKED`、租约接管、6 次指数退避和死信；投影以 `(tenant_id,source_event_id)` 唯一约束幂等。

个人通知 API 只按已认证 principal 返回：商机负责人通知绑定 `user_id`，售前指派通知绑定非空 `person_id`，两类标识不能混用；`SELF/ORG/ALL` 不扩大个人收件箱。点击售前通知先标记本人消息已读，再进入 `/presale/requests/{id}` 真实详情，由售前数据范围二次校验，防止 IDOR。PMS 指派角色属于业务角色，不猜测等同 CRM OIDC 角色；具备 `presale.read`、权威非空 `person_id` 且存在真实当前/历史指派关系即可读取对应任务，未指派资源仍拒绝。基础平台现已支持显式维护租户内唯一的 `pms_person_id`，并在 CRM OIDC Access Token、ID Token 与 UserInfo 中签发 `person_id`；正式 PMS 人员目录数据绑定和生产 OIDC 端到端联调仍待完成。映射缺失时不回退到 `user_id/sub`，售前个人通知和执行人能力继续失败关闭。

指派/改派请求必须携带 `Idempotency-Key`。摘要使用按 `person_id` 稳定排序后的完整目标集合，并绑定 actor、父任务、操作、原因和 version；权限与父任务校验先于重放查询。精确重试返回当前任务投影，不重复结束/新增指派、状态日志或自动完成；跨执行人、跨任务或不同载荷返回 409。

## 5. 前端

人员抽屉展示姓名、personId、部门、角色、技能、有效状态和最近同步时间；停用人员不可勾选。改派页明确显示新增/保留/移出和必填原因。

## 6. 验收

- 未完成两级审批不能指派；非团队负责人返回 403。
- 只允许有效 PMS 人员；重名用 personId 区分。
- 首次指派进入执行中并逐人站内通知；改派的新增/移出事实、个人通知及历史完整，精确幂等重放不重复通知。
- 多人任务在尚有任一当前执行人无有效工时时保持执行中；移出未参与者后满足条件则立即完成。
- 历史执行人的工时不替代新加入执行人的登记要求。
- 同步重复不产生重复人员，失败不清空缓存。
- 并发改派使用 version，冲突返回 409。
