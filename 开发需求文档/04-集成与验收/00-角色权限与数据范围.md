# 角色、权限与数据范围

## 1. CRM 角色

| 角色编码 | 名称 | 默认数据范围 | 关键权限 |
| --- | --- | --- | --- |
| sales | 销售 | SELF | customer/opportunity 读写、presale.create |
| sales_director | 销售总监 | ALL 或 ORG | 客户商机管理、TS 节点1审批、全量查看 |
| team_lead | 团队负责人 | ALL 或 ORG | TS 节点2审批、指派/改派、全量查看 |
| technician | 技术人员 | ASSIGNED | TS 详情、进度、工时 |
| technical_director | 技术总监 | 按服务端范围 | 技术审批、部门/负责人指派与受控接管，须精确权限 |
| project_manager | 项目经理 | 真实指派 | 当前任务执行、工时和完成 |
| crm_super_admin | CRM超级管理员 | 按实际授权 | 管理能力仍逐命令校验，不用角色名替代全部权限 |
| customer_admin | 客户管理员 | ALL | 客户合并/作废/导入，不自动拥有敏感明文 |
| auditor | 审计员 | ALL_READONLY | 审计只读 |

2026-10-22内嵌目录CRM MaxEffectiveRoles=10，Portal=1；technical_lead和implementation_engineer已退出新浏览器角色目录，仅历史兼容分支可能保留。实际角色/权限以internal/platformcatalog/manifests.go、会话及服务层为准；本表为摘要，ASSIGNED/ALL_READONLY不是平台scope_type的字面枚举。

## 3. Portal 角色

外部客户使用portal_customer单角色，内部管理会话使用portal_super_admin单角色；不接受两者混合。平台映射开关可消费customer_ref并核对本地映射；实际客户边界不能由浏览器覆盖。账号项目ISOLATED模式与ACTIVE绑定另行收口。内部管理身份不自动成为客户；反馈处理/备案解锁走独立机器scope，不把设计中的portal_operator/portal_admin当作当前已发布角色。

| 权限 | 范围 |
| --- | --- |
| project.read/export | 本客户项目 |
| project.message.read/send | 本账号在本客户项目中的当前经理站内会话 |
| report.request/read/download | 本客户报告 |
| filing.create/update/submit/read | 本客户备案 |
| evaluation.create/read | 本客户项目 |
| feedback.create/read/reply | 本客户反馈 |
| account.security.manage | 当前账号 |
| portal.filing.unlock / portal.feedback.manage | 仅独立application机器身份，不属于浏览器权限目录 |

## 4. 后端数据范围实现

统一 `Scope` 对象：`TenantID,Mode,UserID,OrgIDs,CustomerID,ResourceIDs`。Repository 只接受 Scope，不接受裸 user-supplied owner/customer 条件。查询构造器必须针对每个资源实现；批量、导出、附件、回调后的文件下载使用相同规则。

## 5. 授权目录交付

CRM 与 Portal 分别生成稳定 `catalog_version/checksum/claims_role_config_hash`，分别使用独立 `authorization.catalog.sync` 机器 Client 发布。Portal 的 `portal_customer` 由 CRM 开通流程通过基础平台受控管理接口分配，但角色定义权仍属于 Portal。角色/权限删除前必须检查存量绑定并提供迁移，不得直接重命名已上线编码。

验收：无角色用户不能进入；Token/会话只包含目标应用权限；前端路由、按钮与后端接口矩阵一致；权限变更在约定时限内生效。
