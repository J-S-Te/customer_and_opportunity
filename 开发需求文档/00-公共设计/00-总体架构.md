# 总体架构与模块边界

## 1. 部署单元

业务域包含两个独立子系统：

| 子系统 | 后端 | 前端 | 数据库 | 公开路径建议 |
| --- | --- | --- | --- | --- |
| CRM 客户与商机 | `crm-server` | `crm-web` | `crm` | `/customer-opportunity` |
| 客户自助门户 | `portal-server` | `portal-web` | `customer_portal` | `/customer-portal` |

TS 售前技术支持是 `crm-server` 和 `crm-web` 内的业务模块，不独立部署、不独立接入身份平台。

## 2. 后端模块化单体

每个 Go 服务采用相同分层，禁止 Handler 直接写 GORM 查询：

```text
cmd/server/main.go
internal/
  bootstrap/       # 配置、日志、DB、路由、任务启动
  middleware/      # request_id、认证、授权、租户、审计、恢复
  platform/        # OIDC、授权目录、UserInfo
  shared/          # 响应、错误码、分页、事务、加密、时钟
  modules/
    <module>/
      model.go      # GORM 持久化模型
      dto.go        # 请求/响应 DTO，不直接暴露 Model
      repository.go # 数据访问接口及 GORM 实现
      service.go    # 业务规则、权限和事务边界
      handler.go    # Gin 参数绑定和响应
      routes.go     # 路由与 permission 绑定
      events.go     # 领域事件/outbox（需要时）
      errors.go     # 模块错误
migrations/
configs/
```

依赖方向：`handler → service → repository → GORM/MySQL`。跨模块只调用公开 Service 接口或领域事件，不能跨模块直接操作表。

## 5. 前端工程

当前生产代码接入已有统一前端仓库，使用 Vue 3、Vite、Vue Router、JavaScript ES Module、原生 `fetch` 和 `node:test`。CRM 与 Portal 是两个独立业务子系统，但当前前端分别作为 `customer_opportunity`、`customer_portal` 模块随统一前端构建；二者的后端、数据库、OIDC Client、本地会话和 Cookie 仍保持隔离。不得把尚未安装的 TypeScript、Pinia、Axios、Element Plus、Vitest、Vue Test Utils 或 Playwright 写成当前已落地技术栈；若未来迁移，须单独立项并保留现有接口和路由兼容。

## 6. 数据与事务原则

- MySQL 8，字符集 `utf8mb4`，时间统一存 UTC、接口返回 ISO 8601，前端按 Asia/Shanghai 展示。
- 金额使用 `DECIMAL(18,2)`，工时使用 `DECIMAL(10,2)`，禁止浮点数落库。
- 所有业务表包含 `id`、`tenant_id`、`created_by`、`updated_by`、`created_at`、`updated_at`、`version`。
- 对需保留的数据使用 `deleted_at` 或业务状态软删除，禁止物理删除。
- 并发更新使用 `version` 乐观锁；编号使用数据库流水表或带唯一索引的安全重试。
- 本地数据更新和事件发布使用 Transactional Outbox，避免“库已提交、消息未发送”。

## 7. 身份边界

- CRM 内部用户必须接入基础平台 OIDC Authorization Code + PKCE，并保存 `platform_user_id=OIDC sub`。
- CRM 后端校验 `tenant_id/roles/permissions/role_config_hash/authz_revision`，不信任前端角色。
- OIDC `sub` 只表示基础平台用户，不等于 PMS `person_id`。基础平台交付并签版权威映射 claim 或查询契约前，CRM 生产会话的 `person_id` 必须留空，售前执行人能力失败关闭，禁止回退用 `sub/user_id` 猜测。
- Portal 外部客户已确认采用基础平台 OIDC Authorization Code + PKCE；Portal 通过 OIDC `sub` 查询本地 `customer_id` 映射，不保存密码、不实现改密、不签发独立身份 Token。
- CRM 通过基础平台受控管理 API 预置外部用户并分配 Portal 应用角色，再通知 Portal 建立 `sub ↔ customer_id` 映射；Portal 本身无自注册入口。
- Portal 建立自己的服务端会话，Cookie 与 CRM/平台隔离；会话有效期不超过关联 Token，并定期通过 UserInfo 或重新登录复核授权。
- 两系统数据库、Cookie、OAuth Client、机器 Client 和 Secret 相互隔离。

## 8. 非功能基线

- 列表/详情读请求 P95 ≤ 2 秒，核心写接口具备 200 TPS 压测基线。
- API 可用性目标 99.9%；外部依赖均设置连接、请求超时和熔断。
- 日志为结构化 JSON，包含 `request_id`、`tenant_id`、`user_id`、模块和错误码，不记录密码、Token、Cookie、Secret、完整手机号或银行账号。
- 关键操作写不可变业务审计；附件下载、报告下载和跨系统回调必须审计。
- 数据库迁移、备份、恢复和回滚在上线前演练。
