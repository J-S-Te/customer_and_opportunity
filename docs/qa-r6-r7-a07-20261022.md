## 已确认根因及修复

### R7 执行人重放

两个入口原先先解析可变目录，把权威姓名、组织快照放进摘要，并在已提交重放前检查新增人员资格。改为排序后的稳定意图（平台用户 ID、执行岗位、客户端明确选定的组织 ID、原因、版本）；展示字段不参与摘要。已提交精确重放在目录解析、冻结/资格复核前返回当前任务投影，不重复指派/事件/通知。

当前调用者权限、租户/请求边界、历史接口规则快照、两级接口当前负责人门禁继续保留；不同原因、明确组织选择或其他意图变化，同键仍冲突。新写入仍解析权威姓名/组织并检查资格，不自动赋权。

限制：升级前以可变快照生成的旧 `request_hash` 没有原始稳定客户端意图，不能安全反推等价请求；这些旧 key 可能返回 409，不伪造回放成功、不自动改写历史账本。

### R6 通知身份

新指派的 `assignee_namespace`、指派事件 `recipient_namespace`、通知投影 `recipient_namespace` 明确为 `USER`。新 USER 执行人的进展事件也使用 `USER`，通过收件类型区分申请人/执行人，worker 校验原指派身份标记并保留标记。

个人列表、未读和已读共享同一平台 `user_id` + `USER` 收件边界，PMS claim 缺失或不同都不影响新通知。其他业务明确需要 PMS 的身份路径保留。

历史记录未可靠区分曾使用的 PMS person_id 和平台 user_id，因此不做 OR 双主体查询、不按当前目录猜映射。历史空命名空间或旧 PERSON 消息仅在已认证 user_id 与 person_id 相同时兼容读取；其他历史行保持原样并隐藏，等待受控核对。旧指派产生的历史事件也不盲目标成 USER。这是有意保留的安全边界，不等于全部历史通知已恢复可见。

### A07 候选职责

CRM owner-directory 新增可选 `assignment_duty=TEAM_LEAD|EXECUTOR`，从现有 `platformcatalog.CRMManifest()` 计算完整履职角色，在平台目录分页前以 `role_code` 投影。候选与保存复核共用同一策略；未知 duty 返回 422，目录不可用失败关闭。路由支持仅持有 `presale.assign` 的合法指派人。

前端负责人和执行人分别传递职责，目录失败时清空旧候选；保存端继续复核资格。前端幂等规范化保留明确的 `department_id`。已只读确认平台目录支持重复 `role_code` 参数，未发现本次所需的接口缺口。
