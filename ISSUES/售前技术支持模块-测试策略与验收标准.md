## 一、测试目标与原则

### 1.1 测试目标
1. 验证"申请—审批—指派—执行—工时"主流程（TS-001~TS-006、TS-010）端到端可用，无阻断性缺陷即可上线。
2. 验证跨子系统契约 **J/K** 的字段、方向、幂等、容错符合《T5》定义，工时成功进入项目管理系统。
3. 验证 **Q4 权限收敛**与状态机边界，杜绝越权数据与非法状态流转。
4. 以 PRD 成功指标为验收门禁（线上发起率、推送成功率、提醒触达率），量化验收而非主观判断。

### 1.2 测试原则
- **风险驱动**：P0（TS-001~006、TS-010）优先覆盖，P1（TS-007、TS-008）次之，P2（TS-009）单独排期。
- **契约优先**：跨系统数据流 J/K 以契约字段表为唯一验收基准，先联调契约后做端到端。
- **数据不造假**：不编造用户声音；测试数据来自 PMS 主数据同步与构造样本，需保留原始登记口径（`raw_unit`/`raw_hours`）供审计溯源。
- **权限为红线**：所有"查看范围/操作按钮"以**后端 `data_scope` + 状态门控**为准，前端不渲染越权入口是兜底而非信任边界。
- **异步不阻断**：数据流 K 推送失败必须不阻断本系统主流程，且可重试、可观测。

## 二、质量风险分析（Risk-Based Testing）

| # | 风险点 | 来源 | 影响 | 等级 | 测试应对 |
|---|---|---|---|---|---|

| R2 | 跨系统契约 J/K 字段/鉴权未联调 | T5 新增流 | 指派人员缺失 / 工时推送失败 | **高** | 契约字段表逐字段断言；MQ 幂等/死信验证 |

| R9 | 联系电话未脱敏的合规争议 | V1.2 决议（不脱敏） | 隐私审计关注点 | 中 | **按决议确认不脱敏、不做字段级权限**；记录于测试报告备注 |

## 三、测试策略

### 3.1 测试层级与类型

| 层级 | 对象 | 重点 | 责任方 | 方法 |
|---|---|---|---|---|
| 单元/组件 | 工时换算、幂等键生成、状态机引擎、审批节点判断 | 纯逻辑正确性 | 开发 | 单测覆盖边界值 |
| 接口（API） | TS 后端接口、通用审批引擎实例、数据流 J/K 契约 | 字段契约、鉴权、错误码 | 开发+QA | 接口自动化（Postman/自研） |
| 集成 | CRM↔PMS（J 同步、K 推送）、审批引擎复用 | 跨系统数据一致、异步容错 | QA+架构 | 联调环境 + PMS Stub |
| 系统（功能/UI） | TS-01~TS-05 页面、商机详情 P-06 增强 | 端到端主流程、权限、异常 | QA | 手工 + 关键路径自动化 |
| UAT | 销售/销售总监/团队负责人/实施工程师真实角色 | 业务可用性、线上发起率采样 | 业务方 | 灰度/UAT 环境 |
| 非功能 | 性能/安全/兼容 | 见 §六 | QA | 专项测试 |

### 3.2 测试环境策略
- **测试环境**：CRM 测试环境 + 审批引擎测试实例。
- **PMS 联调环境**：优先使用 PMS 测试环境；若不可达，采用 **PMS Stub/Mock**（实现 `GET /api/v1/pms/technicians` 与 MQ 消费端），Stub 须实现契约 J/K 的全部字段与鉴权头，并在联调前由架构与 PMS 方 sign-off。
- **数据隔离**：测试数据带 `TEST_` 前缀，推送至 PMS Stub 的时间计划须可清理，避免污染生产统计。
- **MQ**：测试 Topic `crm.presale.worklog.created`（测试命名空间），验证至少一次投递与去重。

### 3.3 测试数据策略
- **人员主数据**：通过数据流 J 同步构造样本（覆盖 技术总监/团队负责人/项目经理/实施工程师 四角色，含 1 条 `validFlag=false` 用于负向用例，重名 2 人以 `personId` 区分）。
  - 样本（复用原型）：`PMS-U10086` 王建国/安全技术部/实施工程师/valid=true；`PMS-U10087` 赵晓燕/安全技术部/实施工程师/valid=true；`PMS-U10050` 李婷芳/测评一部/团队负责人/valid=true；`PMS-U10051` 孙志强/测评二部/技术总监/valid=true（兼技术负责人）；`PMS-U10052` 周慧/安全技术部/项目经理/valid=false。
  - 角色账号：销售=陈浩然、销售总监=刘明、团队负责人=李婷芳、实施工程师=王建国、技术负责人=孙志强。
- **商机数据**：复用宿主 P-06 商机样本（如 `SJ202607070001` 某银行核心系统等保测评售前），含预填 `opportunityId` 跳转。
- **工时样本**：覆盖"人天登记换算为小时""小时登记直推""多次累加""同一人同一天不同任务"以验证幂等键。
- **敏感数据**：联系电话按 V1.2 决议**不脱敏**；测试报告不得外传真实手机号，使用脱敏占位（如 `138****0000`）。

### 3.4 重点测试领域（P0 优先）
1. 主流程贯通：销售发起 → 两级审批 → 指派 → 执行更新 → 工时登记 → 推送 PMS（全状态覆盖）。
2. 跨系统契约 J/K 字段级断言与异步容错。
3. Q4 权限矩阵（5 角色 × 查看/操作）。
4. 状态机边界与负向流转。
5. 工时换算（基准=小时）与幂等。

### 3.5 入口 / 出口标准

**入口标准（可开始系统测试）：**
- 接口契约 J/K 联调通过（字段、幂等、容错）。
- P0 接口自动化冒烟通过，主流程后端无 P0 缺陷。
- 测试环境部署成功，PMS Stub 或测试环境可达。

**出口标准（可上线）：**
- P0 需求（TS-001~006、TS-010）验收用例 100% 通过，无未关闭 P0/P1 缺陷。
- 跨系统 K 推送成功率 ≥ 99%（联调/压测样本）。
- Q4 权限越权用例 0 通过（即全部被拦截）。
- 验收门禁指标（§七）达标。

### 3.6 缺陷分级
- **P0（阻塞）**：主流程断点、越权数据可见、推送丢失且无重试、状态机非法流转。
- **P1（严重）**：跨系统字段缺失/错误、工时换算错误、超时提醒不触发、权限按钮误渲染。
- **P2（一般）**：UI 文案/样式、非关键交互。
- **P3（轻微）**：建议性优化。

### 3.7 回归策略
- 每次发版对 P0 主流程 + Q4 权限矩阵 + 数据流 K 做全量回归。
- 工时换算、幂等键、状态机引擎纳入单测持续集成。

## 四、功能验收标准（Acceptance Criteria）

> 格式：**Given（前置）/ When（操作）/ Then（预期）**，每条含明确 Pass 条件。覆盖 TS-001~TS-010。

### 4.1 TS-001 售前技术支持申请创建（P0）
- **AC-001** Given 销售在「商机详情 P-06」或 TS-01 点击发起，When 进入 TS-02 且从 P-06 进入，Then `opportunityId` 预填且只读、不可改。
- **AC-002** Given 申请表单，When `opportunityId` 为空（异常/越权），Then 禁止进入创建页或禁止提交，并提示"必须关联商机"。
- **AC-003** Given 场地类型选择「现场」，When 未填 `service_address`，Then 提交被拦截，标红提示必填。
- **AC-004** Given 表单，When 联系人/联系电话任一为空，或期望结束时间早于开始时间，Then 提交被拦截。
- **AC-005** Given 全部必填合法，When 点击提交，Then 生成 `request_id`（格式 `TS+YYYYMMDD+4位`），状态置「待审批」，进入 TS-002 审批流。
- **AC-006** Given 申请层表单，When 检查字段，Then **不含**工作内容（方案设计等）字段——工作内容仅在 TS-005 工时层登记（申请层与工时层解耦）。
- **AC-007** Given 提交成功，When 查看 `t_ts_request`，Then `contact_phone` **不脱敏、无字段级权限控制**（V1.2 决议），实施人员可见。

### 4.2 TS-002 两级审批（P0）
- **AC-008** Given 任务「待审批」，When 销售总监（节点1）通过，Then 进入节点2；When 团队负责人（节点2）通过，Then 状态置「已审批待指派」。
- **AC-009** Given 任一节点点击驳回并填写理由，When 提交，Then 状态置「已驳回」（终止），`reject_reason` 留痕，申请人可见。
- **AC-010** Given 已驳回任务，When 任何角色进入，Then 无审批/指派/执行操作按钮，流程不可再推进。
- **AC-011** Given 审批操作，When 完成，Then `t_ts_approve_log` 记录 节点/审批人/结果/意见/时间（复用 V2.0 通用审批引擎实例）。
- **AC-012** Given 非当前审批节点角色（如实施工程师看节点1），When 查看详情，Then 不渲染「通过/驳回」按钮（后端门控）。

### 4.3 TS-003 指派实施工程师（P0）
- **AC-013** Given 状态「已审批待指派」且当前角色为团队负责人，When 从人员池勾选人员（可多人）并提交，Then `t_ts_assignment` 写入 `is_current=true`，状态置「执行中」，通知执行人。
- **AC-014** Given 人员池（TS-05），When 渲染，Then 仅展示 `validFlag=true` 人员；`validFlag=false`（如周慧）不可选；重名以 `personId` 区分。
- **AC-015** Given 已指派任务，When 团队负责人改派，Then 原记录 `is_current=false`，新记录 `is_current=true`，改派历史可追溯。
- **AC-016** Given 指派人员池数据，When 检查来源，Then 来自数据流 J 同步的 PMS 主数据，CRM 不另建军号，`personId` 权威。

### 4.4 TS-004 过程记录与状态机（P0）
- **AC-017** Given 各状态任务，When 核对状态集合，Then 仅允许：待审批→已审批待指派→执行中→已完成；旁支：已驳回/已取消。
- **AC-018** Given 状态「执行中」的执行人，When 更新进度备注（文字/链接），Then 备注写入进度时间线，**不接受方案文档上传**。
- **AC-019** Given 状态「待审批」，When 申请人点击取消，Then 置「已取消」；Given「已审批待指派/执行中」亦可取消→「已取消」；Given「已驳回/已完成」不可取消。
- **AC-020** Given 商机详情 P-06，When 查看「售前技术支持」关联区，Then 只读列出该商机关联任务（任务号/状态/执行人/进度），并含「发起售前支持」入口。

### 4.5 TS-005 工时登记（P0）【基准单位=小时，Q5 已确认】
- **AC-021** Given 执行人进入 TS-04，When 查看，Then 实施人员自动取当前登录技术人员（来自 `t_ts_engineer_pool`），不可改；关联任务只读。
- **AC-022** Given 登记单位可选「人天」或「小时」（系数默认 1 人天 = 8 小时，可配），When 选「人天」填 1.0 并实时换算，Then 显示小时值 `8.0`（小时保留 2 位小数）；When 选「小时」填 8.0，Then 显示 `8.0` 小时，无需换算。
- **AC-023** Given 填写起止时间/工作地点/工作内容（方案设计/技术交流/POC演示/技术答疑/其他），When 提交，Then 写入 `t_ts_worklog`，`raw_unit`/`raw_hours` 保留原始登记口径，`unit`/`workHours` 为换算后小时值（推送 PMS 口径）。
- **AC-024** Given 同一任务，When 执行人多次提交工时，Then 可累加，每次生成独立 `log_id`，均触发推送。

### 4.6 TS-006 工时推送项目管理系统（P0）【unit=小时】
- **AC-025** Given 工时提交成功，When 触发数据流 K，Then 向 `crm.presale.worklog.created` 投递，字段对齐契约 K（含 `implementerDept`/`personName`/`workStartTime`/`workEndTime`/`unit=小时`/`workHours(小时值)`/`workSiteAddress`/`venue`/`workContent`/`idempotencyKey`）。
- **AC-026** Given 同一 (taskId+personId+workDate)，When 重复推送，Then 下游按 `idempotencyKey` 去重，不重复计入。
- **AC-027** Given 推送失败，When 指数退避重试（最多 6 次）后仍失败，Then 进入死信队列，本系统主流程不阻断，工时记录 `push_status=待重试`，站内提示，TS-04 提供手动重试入口。
- **AC-028** Given 推送成功，When 回调，Then `push_status=成功`，TS-04 状态反馈更新。

### 4.7 TS-007 列表与视图（P1）【团队负责人=全部，已确认】
- **AC-029** Given 角色为销售/实施工程师，When 查看 TS-01 视图，Then 仅见"我发起的/我执行的"；Given 销售总监/技术负责人/**团队负责人**，Then 见「全部」。
- **AC-030** Given 任何角色，When 请求越权数据，Then 后端 `data_scope` 过滤，越权项不返回，前端不渲染越权入口。
- **AC-031** Given TS-01，When 使用筛选（商机/人员/状态/场地类型/时间）与看板↔列表切换，Then 结果与筛选条件一致，状态列与 PRD 状态标签色一致。

### 4.8 TS-008 超时预警（P1）
- **AC-032** Given 审批/指派超过可配阈值，When 触发，Then 站内提醒相关节点人，触达可被统计（目标触达率 ≥ 95%）。
- **AC-033** Given 执行超期，When 触发，Then 向任务相关人发送超期提醒。

### 4.9 TS-009 售前投入报表（P2，非上线阻塞）
- **AC-034** Given 月度数据，When 生成报表，Then 输出人力投入、工时趋势、商机售前覆盖率，建立 R3 基线（月度可用）。
- *排期：上线后下一周期，不作为上线门禁。*

### 4.10 TS-010 商机关联展示（P0）
- **AC-035** Given 商机详情 P-06，When 该商机有关联售前任务，Then 「售前技术支持」区列出任务（状态/执行人/进度）只读；无关联时展示空态引导「发起售前支持」。
- **AC-036** Given 点击「发起售前支持」，When 跳转 TS-02，Then `opportunityId` 预填且只读。

## 五、跨子系统契约验收（数据流 J / K）

### 5.1 数据流 J：PMS → CRM 人员主数据同步
| 验收项 | 预期 | Pass 条件 |
|---|---|---|
| 同步方式 | 定时每 6h + 手动刷新（TS-05「刷新人员池」） | 手动触发后展示「最近同步于 HH:mm」；6h 自动同步生效 |
| 写入 | `t_ts_engineer_pool` 覆盖式 upsert by `personId` | 同 personId 重复同步不新增重复行 |
| 字段契约 | personId/personName/department/role/skillTags/contact/validFlag/syncedAt | 逐字段类型/必填与契约 J 一致 |
| 指派可用 | 仅 `validFlag=true` 进入人员池 | 停用人员不可指派 |
| 异常 | 同步失败 | 前端提示失败+重试，不影响已缓存数据 |

### 5.2 数据流 K：CRM → PMS 工时推送【unit=小时，Q5 已确认】
| 验收项 | 预期 | Pass 条件 |
|---|---|---|
| 通道 | MQ 异步（至少一次） | 投递成功，下游消费 |
| 幂等 | `idempotencyKey = taskId + '-' + personId + '-' + workDate` | 重复投递下游去重 |

### 6.1 安全与权限（红线）
- **AC-S1**：5 角色 × 查看/操作矩阵（附录 B）全部用例通过，越权数据后端不返回（0 例外）。

### 6.4 数据准确
- 工时换算精度：小时保留 2 位小数，误差 ≤ 0.01。
- 统计卡（进行中/待我审批/本月工时）与后台数据一致（单位口径已统一为小时）。
