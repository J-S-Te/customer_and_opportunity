# 客户与商机管理业务域

> 当前阶段：CRM、售前和 Portal 核心生产代码已形成，本地基础平台接入闭环可运行；可选外部业务 Provider 仍需逐项联调

CRM 与 Portal 已按两个独立应用内嵌浏览器授权目录，并可使用各自独立的 `authorization.catalog.sync` 机器 Client 发布至基础平台；生产启动会核验 OIDC `role_config_hash` 与当前二进制目录映射，避免平台授权与本地鉴权漂移。部署配置与 hash 查询命令见 [`DEVELOPMENT.md`](DEVELOPMENT.md)。Portal 邀请生成已在首次远程写前建立加密、可恢复的幂等 saga；平台预置、角色分配与 Portal mapping 使用每步稳定键，响应丢失后续跑同一操作，最终邀请和审计原子提交。基础平台已提供外部客户预置、Portal 角色分配/回收 Provider 和 OpenAPI；预置会创建稳定 OIDC `sub` 及一个没有初始密码的 HUMAN/LOCAL 登录账号。平台管理员通过现有账号生命周期显式初始化一次性临时密码，CRM 仅展示登录账号而不接触密码。本地 `customer_portal/dev` 可由平台部署 Agent 自动创建独立数据库、OIDC Client、角色目录和六组最小权限服务 Client；生产仍必须替换为 HTTPS、Secret 管理、生产数据库和正式网络策略。
> 文档基线：CRM PRD V2.1、门户 PRD V1.1、售前技术支持 PRD V1.2
> 最近整理：2026-08-01

本目录承载“客户与商机管理”业务域的需求、原型和测试验收资料。业务域由两个独立子系统及一个内嵌模块组成：

1. **客户与商机管理子系统（CRM）**：面向内部销售及管理人员，负责客户主数据和商机经营；
2. **售前技术支持模块（TS）**：内嵌 CRM，负责售前申请、审批、指派、执行和工时闭环；
3. **客户自助门户子系统（Portal）**：面向外部客户，独立部署，负责项目进度、报告、备案和服务评价。

报价与投标、合同管理、项目服务、项目管理系统均是本业务域的外部协作系统，不在本目录内实现其内部业务。

## CI/CD

`.github/workflows/ci-cd.yml` 在 Pull Request 执行 Go 测试、vet 和 CRM/Portal
OpenAPI 防漂移检查；`main` 分支通过后分别构建 Dockerfile 的 `crm-runtime`
与 `portal-runtime`，推送到 ACR，并使用两个不可变 digest 进入部署步骤。

仓库级 Actions 配置：

- Secrets：`ACR_USERNAME`、`ACR_PASSWORD`；
- Variables：`ACR_PUSH_REGISTRY`、`ACR_PULL_REGISTRY`、`ACR_NAMESPACE`、
  `ACR_REPOSITORY`。

GitHub `test` Environment 配置：

- Secrets：`DEPLOY_HOST`、`DEPLOY_USER`、`DEPLOY_PORT`、`DEPLOY_SSH_KEY`、
  `DEPLOY_KNOWN_HOSTS`；
- Variable：`DEPLOY_PATH`，默认 `/opt/basic-platform`；
- 可选 Variable：`CUSTOMER_DEPLOY_SCRIPT`，默认
  `/opt/basic-platform/bin/deploy-customer-opportunity.sh`。

服务器发布脚本必须由 customer_and_opportunity 的生产部署基线提供，并接收
两个参数：`<crm-image@sha256:digest> <portal-image@sha256:digest>`。脚本负责
双 schema 备份、受控 migration、两个 API 的滚动更新、健康检查和失败回滚；
workflow 不修改 platform 的 Compose 或 `deploy-service.sh`。

## 4. 子系统边界

### 4.1 客户与商机管理子系统（CRM）

CRM 聚焦合同签订前的客户经营和商机培育，保留以下范围：

| 模块 | 编号 | 主要能力 |
| --- | --- | --- |
| 客户信息录入与维护 | CM-001 | 客户档案、查重、导入、合并、敏感字段、操作日志、软删除 |
| 客户查询与检索 | CM-002 | 多维检索、筛选、详情页签、导出 |
| 门户账号开通触发 | CM-004 | 校验联系人、同步创建门户账号、生成/撤销 2 小时注册链接 |
| 商机创建与维护 | BM-001 | 商机档案、金额、来源、需求、竞争信息、团队、附件、转合同 |
| 商机跟进与阶段 | BM-002 | 七阶段看板、跟进记录、直接推进/回退、超时预警和终态管理 |

CRM 不实现：

- 报价单编制、审批和版本管理；
- 投标、标书、保证金和开标业务；
- 客户门户页面及门户内部账号管理；
- 合同正文及合同生命周期；
- 项目执行过程；
- 报告文件生成。

### 4.2 售前技术支持模块（TS）

TS 是 CRM 内嵌的轻量协调模块，只处理“派工 + 过程记录”最小闭环：

```text
销售发起
  → 销售总监审批
  → 团队负责人审批
  → 团队负责人指派/改派技术人员
  → 执行人更新进度
  → 执行人登记工时
  → 工时异步推送项目管理系统
```

TS 不管理方案文件、技术标、知识库、模板库或 POC 资产，也不自动推动商机阶段。

### 4.3 客户自助门户子系统（Portal）

Portal 面向外部客户，是独立部署和独立验收的外部访问面：

| 模块 | 编号 | 主要能力 |
| --- | --- | --- |
| 门户访问控制 | CP-001 / PO-08 | 注册链接绑定、基础平台 OIDC 登录、本地会话和账号安全 |
| 项目进度 | CP-002 | 项目列表、详情、里程碑、动态、延期预警和项目经理入口 |
| 电子报告 | CP-003 | 报告申请、下游审批、加密发放、限时下载和审计 |
| 等保备案 | CUS-004 | 7 步向导、校验、暂存、备案材料和提交锁定 |
| 服务反馈 | CP-004 | 4 维评价、评语和低分告警；异议/投诉/建议反馈、处理时间线和 24 小时 SLA |

Portal 不维护客户主数据、不管理商机、不执行项目、不生成原始报告文件，也不提供客户自注册。

## 5. 管理端功能

### 5.1 客户管理

管理端原型提供客户列表和客户详情，目标生产能力包括：

- 客户编号规则：`KH + YYYYMMDD + 4 位流水`；
- 新建时按客户名称模糊匹配、统一社会信用代码精确查重；
- 客户档案覆盖基础、业务、组织、干系人、信息系统和财务等信息；
- 客户详情支持基本信息、干系人、商机历史、项目历史、沟通记录等页签；
- 客户档案支持 Excel 导入、导出、合并和软删除；
- 敏感字段加密落库，并根据角色脱敏展示；
- 字段变更写入不可静默覆盖的操作日志；
- 客户及商机档案软删除后保留 6 年，客户操作日志和沟通记录永久保留。

> 信用评级功能 CM-003 已删除，管理端和门户原型中的相关字段、筛选、徽标及统计展示已同步清理。

### 5.2 门户账号开通触发

CRM 客户详情保留“生成注册链接”入口，当前 ISSUES 基线定义：

1. 客户必须存在登记联系人且联系电话非空；
2. CRM 通过基础平台受控接口预置外部用户并分配 Portal 角色，再同步 Portal 建立 `OIDC sub ↔ customerId` 映射；
3. CRM 生成不可枚举的注册链接，默认有效期 2 小时；链接只承载邀请上下文，不承载密码；
4. 链接状态包括待使用、已使用、已过期、已撤销；
5. 重新生成后旧链接立即失效；
6. 生成、使用、撤销过程必须审计；
7. Portal 不提供自注册入口。

Portal 外部客户已确认采用基础平台 OIDC。固定初始口令、Portal 本地密码哈希、独立 `portal-jwt` 和 Portal 强制改密方案均废止；密码设置、找回、锁定和 MFA 由基础平台统一身份能力负责。

### 5.3 商机管理

商机编号规则为 `SJ + YYYYMMDD + 4 位流水`。商机保留客户、类型、来源、预计金额、预计签单时间、需求、竞争信息、团队、附件和跟进记录。

商机阶段共 7 个：

```text
初步接触 ↔ 需求沟通 ↔ 方案制定 ↔ 报价 ↔ 投标
                                      ├→ 已签约
                                      └→ 失败
```

关键规则：

- 5 个推进阶段允许推进与回退；
- 所有商机阶段变更均不需要审批，有权用户提交后立即生效并记录变更日志；
- 已签约和失败是互斥终态，对应 `opp_status=已关闭`；
- 人工进入已签约时必须关联同一客户的合同，人工进入失败时必须填写标准失败原因；
- 报价/投标可信回传可以直接进入终态：中标缺少合同时进入“已签约”并标记“待关联合同”，落标缺少原因时进入“失败”并标记“待补原因”；
- 已签约/失败可由有权用户直接调整或重开，无需审批，但必须记录原阶段、目标阶段、原因、操作人和时间；
- 报价/投标的实际业务在外部子系统执行，CRM 只负责调起和展示只读状态；
- 报价与投标子系统的中标/落标回传可直接驱动已签约/失败；合同和失败原因缺失时作为终态待办补充，不阻断阶段变更；
- 商机预计金额与最新已通过报价不一致时只提示，不阻断签单；
- 售前任务只关联展示，不自动推动商机阶段。

## 6. 售前技术支持功能

### 6.1 申请

- 必须关联商机；从商机详情进入时自动预填且只读；
- 字段包括场地类型、服务地址、联系人、联系电话、需求描述、期望起止时间和紧急度；
- 场地为“现场”时服务地址必填；
- 联系人和联系电话必填，期望结束时间不得早于开始时间；
- 工作内容不属于申请层，放在工时登记层；
- 任务号规则：`TS + YYYYMMDD + 4 位流水`。

### 6.2 审批与指派

- 审批节点固定为销售总监 → 团队负责人；
- 两级均通过后进入“已审批待指派”；
- 任一节点驳回后任务终止，并保存驳回原因；
- 团队负责人从项目管理系统同步的技术人员池中指派，可多人、可改派；
- 改派保留完整历史；
- 仅 `validFlag=true` 的人员可被指派，重名以 PMS `personId` 区分。

### 6.3 执行与工时

- 执行人可追加文字/链接形式的进度记录；
- 不提供方案文件上传；
- 一个任务可以多次登记工时；
- 登记单位可选“人天”或“小时”；
- **最新确认的权威推送单位为小时**；
- 默认按 `1 人天 = 8 小时` 换算，系数可配置；
- `rawUnit/rawHours` 保留原始登记值，`unit/workHours` 保存并推送换算后的小时值；
- 工时通过数据流 K 异步推送项目管理系统；
- 失败最多指数退避重试 6 次，随后进入死信；
- 单人指派时，执行人提交首笔有效工时后任务自动完成；多人指派时，所有当前执行人均至少提交一笔有效工时后任务自动完成；
- 未实际参与的当前执行人须由团队负责人先移出当前指派，否则任务继续保持“执行中”；
- 工时推送与任务完成解耦：推送失败不阻断任务自动完成，工时状态显示“待重试”并提供手动重试。

### 6.4 状态机

```text
待审批 → 已审批待指派 → 执行中 → 已完成
   └→ 已驳回

待审批 / 已审批待指派 / 执行中 → 已取消
```

任务采用自动完成规则：单人指派时，执行人提交首笔通过校验的工时后直接完成；多人指派时，系统在每次有效工时提交或当前指派集合变更后检查，只有所有当前执行人均已有至少一笔有效工时才进入“已完成”。未实际参与者需要团队负责人先移出当前指派。PMS 推送是异步动作，推送失败只改变对应工时的推送状态，不回滚已完成任务。

TS-009 已提供按租户和 UTC 日窗口可重跑的日报事实投影 Worker，保留历史人员/部门快照、PMS outbox 分母和每次运行证据。正式投影新鲜度与降级策略签版前，在线报表仍读取权威明细；异步文件导出未配置对象存储时继续明确返回 503，不生成虚假任务或下载地址。

### 6.5 角色视图

| 角色 | 查看范围 | 主要操作 |
| --- | --- | --- |
| 销售人员 | 自己发起的任务 | 创建申请、查看进度、符合规则时取消 |
| 销售总监 | 全部 | 审批节点 1 |

## 7. 门户端功能

### 7.1 激活、登录与账号安全

Portal 采用“CRM 预置基础平台外部用户 + 注册链接绑定 + 基础平台 OIDC + Portal 本地会话”模型：

- Portal 无自注册入口；
- CRM 通过基础平台受控接口预置外部用户，为 Portal 应用分配 `portal_customer` 角色，并同步 Portal 保存 `platform_user_id/OIDC sub ↔ customerId` 映射；
- CRM 生成 2 小时一次性注册链接；Portal 校验后将邀请上下文绑定到 OIDC `state`，再跳转基础平台授权端点；
- Portal 使用 Authorization Code + PKCE，严格校验 state、nonce、issuer、audience、签名、有效期和 `token_use`；
- OIDC 回调的 `sub` 必须与邀请预置用户一致，成功后消费邀请并建立 Portal 自己的服务端会话；
- Portal 不保存或校验客户密码，不签发独立身份 Token；密码设置、找回、失败锁定和 MFA 由基础平台负责；
- Portal 会话有效期不得超过 OIDC Token，有效期建议最长 15 分钟，并通过 UserInfo/重新登录及时收敛授权；
- 展示上次登录时间、IP、属地和设备；
- 登录、OIDC 回调、退出、会话撤销和异常访问写不可篡改审计日志；
- 客户只能访问绑定 `customerId/data_scope` 下的资源。

### 7.2 工作台与项目进度

- 工作台展示进行中项目、已完成项目、待下载报告和待评价数量；
- 项目列表展示编号、名称、合同号、状态、进度和预计完成时间；
- 项目详情展示概览、总体进度、5 阶段里程碑、近期动态和项目团队；
- 延期项目展示预警；
- 项目数据来自项目服务子系统只读快照，目标延迟不超过 5 分钟；
- Portal 不修改项目执行数据；
- 项目进度 PDF 导出和站内联系项目经理为 P1。

当前生产代码已实现 tenant/customer 隔离的项目详情、里程碑、团队脱敏信息和独立动态分页；前端将项目主档、动态和评价拆分加载，评价权限不足或服务失败不会遮蔽项目详情。项目进度 PDF 采用不可变快照、异步任务、过期租约接管和 15 分钟账号绑定的一次性下载授权；渲染器未配置时 Worker 启动失败，生成失败落明确失败态，不返回占位 PDF。站内联系项目经理使用项目来源权威提供的 `manager_portal_account_id`，会话、消息、审计、持久幂等、限流和当前经理事务复核均已实现；消息历史使用不透明游标的稳定 keyset 分页，每条真正显示给当前账号的接收消息单独记录已读，不会跨过未加载旧消息。姓名和脱敏联系方式不能推导接收身份，项目来源未提供账号时入口安全关闭。正式项目服务同步、经理端机器工作台 UI 联调、浏览器 E2E 和生产性能验收仍待完成。

### 7.3 电子报告

- 客户选择项目、报告类型、申请原因和接收邮箱后提交；
- 下游项目经理负责审批和原始报告生成；
- Portal 接收回调并完成 AES-256 加密存储；
- 默认生成 72 小时有效下载链接；
- 支持水印、异常下载冻结和完整发放/下载留痕；
- 报告申请、文件和下载接口必须按当前客户二次鉴权，禁止 IDOR。

当前生产后端已实现报告申请/列表/详情、本地状态投影和异步投递机制，并通过 `000038` 为新建及后续状态变化在同一事务追加不可变事件；详情仅向当前 tenant/customer 返回最小状态时间线。机器回调 tenant 与认证主体强绑定，历史幂等键按载荷摘要安全重放或拒绝冲突。迁移不为存量报告伪造 actor、来源或发生时间，因此历史报告可能没有事件。`000039` 已增加最长 72 小时、按 tenant/customer/report/account 绑定的下载 grant、过期/冻结/撤销状态、只存摘要的高熵 token 和 append-only 下载审计；非法长度和错误 token 均有界审计，不存在/越权报告统一 404；数据库文件大小在分配缓冲前再次限制为 50 MiB，`000041` 将申请/grant 操作人列对齐 128 字节账号上限。下载凭证只通过受控 POST 的 `X-Report-Download-Token` 头短暂传递，不进 URL、请求体、Authorization、数据库明文或前端持久状态。前端已实现真实项目选择、申请/列表/详情、中文状态时间线、读写下载权限分离和受控 PDF 下载；可信对象存储读取/信封解密、AES 文件加密、可追踪水印、风险网关/GeoIP 规则及正式项目服务联调仍未完成，因此当前运行时在授权校验后返回 503 并留下失败审计，不生成伪文件。

### 7.4 等保备案

备案原型依据《网络安全等级保护备案表（2025 版）》拆成 7 步：

1. 单位基本情况；
2. 定级对象情况；
3. 定级情况；
4. 新技术应用；
5. 提交材料；
6. 数据摸底；
7. 定级报告。

正式需求包括实时校验、草稿暂存与恢复、备案 PDF 生成、等级矩阵单选交互，以及提交后锁定。提交后的修改必须走管理员解锁流程，该流程归属和时效仍需确认。

### 7.5 服务评价与反馈

- 服务评价包含专业能力、响应速度、报告质量和服务态度 4 个维度，每项 1～5 星；
- 可填写可选评语；
- 评价数据永久保留并做匿名化统计；

- 异议、投诉、建议反馈要求 24 小时响应和超时升级；
- 生产代码已提供 Portal 反馈创建、本人列表/详情、追加沟通、处理状态时间线、持久幂等的解决后关闭以及 24 小时 SLA Worker；内部客服工作台、正式 machine scope、附件与外部通知仍待交付。

## 11. 已确认的重要决策

- CRM、Portal 是独立子系统；TS 是 CRM 内嵌模块；
- Portal 外部客户统一采用基础平台 OIDC；Portal 仅维护 `OIDC sub ↔ customerId` 业务映射和本地会话，不维护客户密码；
- 报价与投标已从 CRM 剥离；
- 门户不提供自注册；
- 商机阶段为 5 个推进阶段 + 已签约/失败两个终态；
- 人工进入已签约必须关联合同，人工进入失败必须填写原因；外部可信回传不受此项阻断；
- 中标回传缺少合同时直接进入已签约并标记“待关联合同”；
- 落标回传缺少原因时直接进入失败并标记“待补原因”；
- 所有人工商机阶段调整（含推进、回退、进入终态和终态重开）均无需审批，提交后立即生效并审计；
- 报价金额与商机预计金额不一致时只提示、不阻断；
- 信用评级 CM-003 已整体删除；
- TS 两级审批复用通用审批引擎；
- TS 技术人员池来自 PMS 数据流 J；
- 销售/实施仅看自己，销售总监/团队负责人/技术负责人看全部；
- 工时推送基准单位为小时，1 人天默认换算 8 小时；
- 单人指派首笔有效工时自动完成；多人指派须所有当前执行人均至少登记一笔有效工时后自动完成；PMS 推送失败不回滚任务状态；
- TS 联系电话普通详情只显示掩码；拥有独立 CRITICAL 权限且具备当前/历史真实指派关系，或属于明确管理角色时，才可显式按需查看。审计员禁止查看；每次返回明文前必须完成不含电话的隐私审计，响应不可缓存，页面关闭即清除；
- 本期不接 IM、短信等三方通知，通知以站内消息为主；
- 本期只支持桌面端，不包含移动端和响应式适配。

## 12. 待统一或待补齐事项

以下问题不应由原型实现自行假设：

1. T5 中 D/E/F 的归属需从 CRM 正式修订为 Portal；
2. T5 需补充 P2“查询客户档案摘要”的正式字段契约；
3. T5 K 流的旧示例仍有“人天/supportType”字段，需统一为最新“小时/venue/workContent”口径；
4. Portal 客户反馈内部处理端归属、附件安全链路和外部升级通知；
5. 备案提交后的管理员解锁流程、审批归属和时效；
6. 报告异常下载冻结规则及其执行方；
7. Portal 是否展示报价单或合同；
8. 合同、报价投标、项目服务和 PMS 等团队需在联调前提供 Mock 和正式鉴权方案。

## 13. 建议开发顺序

1. **工程与安全底座**：确认子系统承载模式、身份方案、租户模型、权限目录、审计和统一错误协议；
2. **CRM 客户主数据**：客户建档、查重、查询、详情、日志、加密和数据范围；
3. **CRM 商机闭环**：商机建档、七阶段直接变更、终态待办、变更审计、合同 L、报价投标 G/H/I；
4. **TS 售前闭环**：申请、审批、多人指派/改派、进度、工时自动完成、J/K；
5. **Portal 核心 P0**：激活登录、项目进度、报告申请与安全下载；
6. **Portal P1**：备案、评价、反馈、导出和异常告警；
7. **上线加固**：自动化测试、性能、安全、等保、备份恢复、灰度和回滚演练。
